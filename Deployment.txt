Quiero que prepares este proyecto para poder desplegarlo en una máquina AWS EC2 con Ubuntu usando Docker Compose.

Contexto del proyecto:

* Es un proyecto web compuesto por varios servicios.
* Hay un frontend, un backend Laravel/admin, WordPress/blog, base de datos y Nginx como reverse proxy.
* Actualmente Nginx enruta varios servicios por prefijos, por ejemplo frontend en `/`, backend/admin, WordPress en `/blog` y phpMyAdmin en `/phpmyadmin`.
* El despliegue objetivo será una EC2 Ubuntu donde quiero poder clonar el repositorio, configurar variables de entorno y levantar todo con Docker Compose.
* La rama importante del proyecto es `develop`.

Objetivo:
Dejar el proyecto preparado para producción/despliegue en AWS EC2 Ubuntu, sin modificar código funcional de la aplicación y sin generar documentación Markdown de despliegue.

Restricciones importantes:

* No crees documentación `.md`.
* No crees archivos tipo `DEPLOY_EC2_UBUNTU.md`, `README_DEPLOY.md` ni similares.
* No cambies lógica de negocio.
* No cambies controladores, modelos, vistas Blade, componentes React, rutas funcionales de Laravel o WordPress salvo que sea estrictamente necesario para configuración de despliegue.
* No cambies el comportamiento de la aplicación.
* No borres servicios existentes si son necesarios para desarrollo.
* Si necesitas adaptar algo, hazlo mediante archivos Docker, Compose, Nginx, `.env.example`, scripts de entrada o configuración de despliegue.
* No subas credenciales reales.
* No crees archivos `.env` con secretos reales.
* No uses `chmod 777` como solución general.
* phpMyAdmin no debe quedar expuesto públicamente en producción.
* No hagas commit automáticamente.

Tareas a realizar:

1. Revisar la estructura actual del proyecto y los archivos Docker/Compose/Nginx existentes.

2. Crear o adaptar una configuración de producción para Docker Compose:

   * Puede ser `compose.prod.yaml`, `docker-compose.prod.yml` o el nombre que encaje mejor con el proyecto.
   * Debe estar pensada para ejecutarse en una EC2 Ubuntu.
   * Solo el contenedor Nginx/proxy debe exponer puertos públicos, normalmente `80:80` y opcionalmente `443:443`.
   * Los servicios internos deben usar `expose` o red interna, no `ports` públicos innecesarios.
   * La base de datos debe tener volumen persistente.
   * WordPress debe tener volumen persistente para sus datos, especialmente `wp-content` o el directorio necesario.
   * Laravel debe conservar persistencia donde corresponda, especialmente `storage` si aplica.
   * Añadir `restart: unless-stopped` a servicios de producción.
   * Usar una red Docker propia para el proyecto.
   * phpMyAdmin debe quedar desactivado por defecto en producción, idealmente mediante `profiles: ["debug"]` o una alternativa segura.

3. Revisar el frontend:

   * No usar Vite dev server en producción si actualmente se está sirviendo en el puerto `5173`.
   * Preparar un `Dockerfile.prod` si hace falta.
   * El frontend debe compilarse con `npm run build` y servirse mediante Nginx o un servidor estático adecuado dentro del contenedor.
   * Adaptar el upstream de Nginx para que apunte al puerto correcto de producción, por ejemplo `frontend:80` en vez de `frontend:5173`, si corresponde.

4. Revisar Laravel/backend:

   * Preparar configuración Docker de producción si hace falta.
   * Asegurar que `storage/` y `bootstrap/cache/` tienen permisos correctos dentro del contenedor.
   * No usar `chmod 777`.
   * Si hace falta, crear un `entrypoint.sh` para:

     * Crear carpetas necesarias de Laravel.
     * Ajustar permisos de `storage` y `bootstrap/cache`.
     * Ejecutar caches de Laravel de forma segura si procede.
   * No ejecutar migraciones automáticamente en cada arranque salvo que esté claramente justificado.
   * Preparar `.env.production.example` o actualizar `.env.example` con variables necesarias para producción:

     * `APP_ENV=production`
     * `APP_DEBUG=false`
     * `APP_URL`
     * variables de base de datos
     * configuración de sesiones/cookies si aplica
   * No incluir claves reales.

5. Revisar WordPress:

   * Asegurar persistencia de datos.
   * Preparar variables de entorno necesarias.
   * Si WordPress va bajo `/blog`, dejar preparada la configuración para `WP_HOME` y `WP_SITEURL` mediante variables o configuración segura.
   * No hardcodear un dominio real obligatorio; usar placeholders como `https://TU_DOMINIO.com/blog`.

6. Revisar Nginx:

   * Crear un archivo de configuración de producción, por ejemplo `default.prod.conf`.
   * Mantener el reverse proxy para frontend, backend/admin y WordPress.
   * Evitar exponer phpMyAdmin públicamente en producción.
   * Preparar cabeceras proxy correctas:

     * `Host`
     * `X-Real-IP`
     * `X-Forwarded-For`
     * `X-Forwarded-Proto`
     * `X-Forwarded-Host`
     * `X-Forwarded-Prefix` cuando corresponda.
   * Dejar preparado soporte para dominio real.
   * Si se deja preparado HTTPS, que sea compatible con Certbot o que quede listo para añadirse después sin romper la configuración HTTP inicial.

7. Revisar seguridad de despliegue:

   * Asegurar que en producción no se exponen públicamente puertos internos como:

     * MySQL/MariaDB.
     * Laravel interno.
     * Vite.
     * phpMyAdmin.
   * Solo Nginx/proxy debe ser accesible desde fuera.
   * phpMyAdmin debe estar desactivado, protegido o solo disponible con profile/debug.

8. Revisar variables de entorno:

   * Añadir o ajustar archivos de ejemplo necesarios.
   * No crear archivos con secretos reales.
   * Usar placeholders claros:

     * `TU_DOMINIO.com`
     * `CAMBIAR_PASSWORD`
     * `GENERAR_APP_KEY`
     * etc.
   * Asegurar que las variables son coherentes con los nombres de servicios definidos en Docker Compose.

9. Ejecutar comprobaciones razonables:

   * Validar sintaxis de Docker Compose.
   * Revisar que los nombres de servicios usados en Nginx coinciden con los del Compose.
   * Revisar que no hay puertos internos expuestos innecesariamente.
   * Revisar que no se han incluido secretos.
   * Revisar que no se ha generado documentación `.md`.
   * Revisar que no se ha modificado código funcional de la aplicación.

Resultado esperado:

* El proyecto debe quedar preparado para ejecutarse en una EC2 Ubuntu con Docker Compose.
* Debe haber una configuración clara de producción.
* No debe generarse documentación Markdown.
* No debe modificarse código funcional de la aplicación.
* Todos los cambios deben estar orientados a despliegue, Docker, Nginx, variables de entorno, permisos y configuración de producción.

Al final, dame un resumen de:

* Archivos creados.
* Archivos modificados.
* Cambios principales.
* Comandos básicos para levantar el proyecto en EC2, sin crear un `.md`.
